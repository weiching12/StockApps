# Cloudflare 免費方案限制（每次修改前必讀）

本專案部署在 Cloudflare **免費方案**。任何會新增或改變 Worker、Durable Object、D1、KV 存取或排程工作的修改，**動手前先讀本文件，完成後依下方檢查表逐項確認**。超過限制時，排程同步、研究擷取或 API 會直接失敗，正式站資料就不會更新。

2026-11-13 曾發生 D1 超出操作限制，原因與修正見文末〈事件紀錄〉。

## 限制一覽

| 資源 | 免費方案上限 | 超過時 |
|---|---|---|
| D1 每次執行查詢數 | **50 個**（Worker 的一次請求或排程、Durable Object 的每一個請求各自計算） | 該次執行的後續查詢失敗 |
| D1 每日讀取 | **500 萬列**（UTC 00:00，台灣 08:00 重置） | 當日所有 D1 查詢失敗 |
| D1 每日寫入 | **10 萬列**（索引更新也算寫入） | 當日所有寫入失敗 |
| D1 單一資料庫大小 | **500 MB** | 無法再寫入 |
| D1 單一值／列大小 | 2 MB；單一 SQL 語句 100 KB；綁定參數 100 個 | 該查詢失敗 |
| 對外請求（fetch） | 每次執行 **50 個** | 該次執行失敗 |
| KV 每日讀取 | 10 萬次 | 讀取失敗 |
| KV 每日寫入／刪除 | **1,000 次** | 寫入失敗（行情無法發布） |
| Worker CPU 時間 | 每次執行 10 ms | 執行中斷 |
| Cache API | `*.workers.dev` 網域**無效** | 不要用 Cache API 做快取 |

「讀取列數」是 D1 實際掃描的列數，不是回傳筆數。沒有走索引的 `WHERE`、`COUNT(*)`、`DELETE`、整表彙總都會掃描整張表。

## 目前用量（2026-11-13 於本機 workerd/D1、全市場規模實測）

| 工作 | 每次 D1 查詢 | 每次讀取列數 | 頻率 |
|---|---|---|---|
| 行情分組階段（每分鐘 32 組） | 約 34 | 數百 | 每輪 4 分鐘 |
| 進場研究擷取 | 約 13 | 約 7 萬（上限為最近 35 個交易日） | 每日 2～3 次 |
| 策略回測（快取未命中） | 6 | 約 26 萬（30 個交易日樣本），半年約 100 萬以上 | 每個條件、每個擷取版本一次 |
| 樣本列表（快取未命中） | 2 | 約 3 萬 | 同上 |
| 同步完成後的每分鐘排程 | 3～5 | 個位數 | 約 200 次／日 |
| Web Push | 每則 1 個寫入 | — | 每次最多 10 則 |

KV 寫入：每輪發布 128 組分組加上刪除舊分組，每天約 530 次，**剩餘空間不大**，不要再把快取或計數器放進 KV。

儲存空間：進場研究保留半年約 330～380 MB；T86 原始報表與版本紀錄目前不會自動刪除。合計接近 500 MB 前，必須縮短研究保留期或清理舊 T86 原始資料。

## 修改前檢查表

1. **每次執行的查詢數**：逐一數這次修改後，一次排程或一次 Durable Object 請求會下幾個 D1 查詢、幾個對外 fetch。迴圈內逐筆查詢是最常見的超限原因；改用 `IN (...)`、`json_each(?)` 一次處理多筆，保持在 **40 個以下**（預留餘裕）。
2. **讀取列數**：新的查詢先用 `EXPLAIN QUERY PLAN` 確認是 `SEARCH ... USING INDEX`，不是 `SCAN`。會隨資料累積而變大的查詢（整表彙總、清理舊資料）必須有上限或快取。
3. **頻率**：排程每分鐘執行一次（台灣 18:30～23:59 約 330 次／日）。同步完成後每分鐘都會再跑的程式，必須在第一個查詢就判斷「已完成」並立即結束；失敗重試要有冷卻時間，不能每分鐘全量重跑。
4. **API 讀取**：使用者每次開頁都會觸發的 D1 查詢，要確認一次讀幾列、乘上可能的瀏覽次數是否接近每日 500 萬列。資料只在擷取或同步後才變動的結果，要快取在 Durable Object（例如 `MARKET_SUMMARY` 的獨立實例），以資料版本為鍵。
5. **寫入列數**：大量寫入時，每列加上每個索引都算一次寫入。相同內容不要重寫（比對 Hash 或用 `INSERT OR IGNORE`）。
6. **KV**：新增 KV 寫入前，確認每天總寫入仍遠低於 1,000 次。
7. **儲存**：新增會每天成長的資料表時，要同時定義保留期限與清理方式，並估算半年後的大小。
8. **驗證**：用 `wrangler.getPlatformProxy()` 在本機 workerd/D1 以全市場規模跑一次，讀 `meta.rows_read`、`meta.rows_written` 與查詢數；必要時把查詢數上限寫成單元測試（參考 `tests/history-repository.test.js` 的分組階段測試）。

## 事件紀錄：2026-11-13 D1 超出操作限制

在本機以全市場規模量測，找出五個超過或逐漸逼近上限的路徑，已在 commit `c9eac3b` 修正：

| 路徑 | 修正前 | 修正後 |
|---|---|---|
| 行情分組階段：每組 3 個查詢 | 每次排程約 96 個查詢（超過 50） | 前後版本各一個查詢，約 34 個 |
| 策略回測：每次載入彙總全部樣本、無快取 | 每次約 26 萬列，半年後 100 萬列以上 | 依擷取版本快取於 `stock-insight-research-cache` |
| 樣本列表：每頁排序全部樣本 | 每頁約 3 萬列 | 同上快取 |
| 研究擷取清理舊資料：全表掃描 | 約 12.7 萬列且隨保存天數成長 | 先查執行紀錄表，走日期索引，約 7.2 萬列且不再成長 |
| 研究擷取寫入：每 200 筆一個查詢 | 34 個查詢且隨資料成長 | 約 1 MB 一組，13 個 |
| Web Push：一次最多 500 則 | 訂閱超過約 20 人就超過對外請求上限 | 每次 10 則，iOS 推播等瀏覽器送完 |

尚待決定：資料庫大小接近 500 MB 時的保留策略（見〈目前用量〉）。
